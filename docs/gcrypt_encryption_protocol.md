# The Gcrypt Encryption Protocol

The Gcrypt Encryption Protocol relies on the latest versiopn of [Gcrypt](https://github.com/TBCMDev/gcrypt).

> If you're having trouble with the API, you can have a look at the cross platform support in Gcrypt, which offers JNI (Java/Kotlin) and webassembly support currently. These are wrapper implementations that provide more examples as to how the functions should be implemented.

## The process

Alice and Bob are two users who want to talk to each other securely. Alice and bob both talk to a server, of which holds information about each person. More specifically, their public keys. Information that can be shared publicly, it is represented in gcrypt as a `pqxdh::public_server_payload`, and is sent to the server once, upon signup / first initialization.

She can do this using gcrypt by calling `pqxdh::make_lkb` to first initialize all of the public and private keys that Alice needs to work with the protocol. She then invokes `pqxdh::make_server_payload` bundle the important public keys together and tell the server about them. She then sends them to the server.

### Step 1

Alice wants to talk to Bob. To do this, she first fetches this `foreign_prekey_bundle` payload from the server.

> This is a different kind of payload. In the payload sent to the server, it contains lots of public one time keys that anyone can take from the server to use **only once**, to initiate a chat with the owner of that key.

Once she has the payload, she calls:
```cpp
gcrypt::create_outbound_session(const gcrypt::xckeypair &localIdentityKey,
                                const gcrypt::xckey &identityToVerifyAgainst,
                                const gcrypt::pqxdh::foreign_prekey_bundle &keys)
```
> The identity to verify against key is equal to the identityKey found in the prekey bundle only if you have no long term token with the person you are trying to talk to. If you've known them before, you should use their old keys to verify that the keys are in fact generated by them.

This makes sure the server data is correct and that the keys are valid, and returns a `session_init_result`.

If the session_init_result is not null, the session was successfully created in memory. Along with this, you have the necessary data needed in this structure to now send the initial message to Bob.

### Step 2 - The initial message

The `session_init_result` contains two members:

```cpp
struct session_init_result
{
    messaging_session session;
    initial_message_handshake handshakeMessage;
};
```

It contains the `messaging_session`, and the `initial_message_handshake`. It is your responsibility to store the messaging_session securely, and let Gcrypt interface with this session, even after a restart.

This is because Gcrypt does not store its sessions. **You must write this functionality**. For more detail about this, skip to [the section on storing messaging sessions](#storing-messaging-sessions)

Now Alice sends this initial message handshake to Bob.

> After this, if everything was sent, Alice can forget about the `handshakeMessage`.

Bob now has this handshake, and can call `create_inbound_session(handshakeMessage)`.

If these steps work, we now have successfully notified each party about the keys they need, and can start chatting, well not quite.

## Storing Messaging Sessions

Messaging sessions need to be stored client side, along with the keys used to create this session.

### Saving the local keys

When you first sign up, your client side public and private keys are generated. These keys need to be stored securely, preferably encrypted with a password hash and salt to ensure nobody can read them without proper credentials.

### Saving the handshake

If Alice grabs Bobs `foreign_key_bundle` to try chat to him, and it was a success, Alice should save this bundle for later if she ever wants to chat with him again. She should treat this as long term storage.
